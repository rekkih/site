# maimai KOP8th history

The qualifying-results section is automatic. Both official schedules close on 23 November 2026 at 23:59 JST, represented as the exclusive boundary `2026-11-24T00:00:00+09:00`. Before then, the section is hidden. After closing, it waits for an archived SEGA snapshot dated at or after that boundary, then displays the top two International or top seven Japan finishers, plus a separate Japan LCQ list for places 8–15. It uses the latest eligible snapshot, preserves SEGA's ordering for tied ranks, and waits if leading places are missing. These are qualifying positions from the feed, not confirmation that finalists completed registration or attended. No moderator action or additional API/storage is needed. Rules: https://maimai.sega.jp/kop8th/maimai/ and https://maimai.sega.com/kop8th/maimai_itr_en/.

Download the full stored history and audit data as CSV from `/api/maimai/kop8th/csv`, linked in the page’s “About this history” section. Both versions are included by default; `?server=ex` or `?server=m` limits the export. The version 3 CSV has readable column names, percentage scores, explicit date zones, original and site ranks, current statuses, removal times, and complete original JSON. Filter `Record type` to `Score` for normal score analysis, then `Used in leaderboard history` to `Yes` to exclude alternate observations. See [the CSV field guide](maimai-csv.md) for row types, units, and audit semantics. Downloads read storage only: no upstream fetch, database writes, or on-download migration. An entirely empty namespace returns 404; removal-only or check-only histories are downloadable. Unavailable records return 503 rather than a partial export.

`/maimai/kop8th` defaults to International. `?server=ex` selects International and `?server=m` selects Japan Ver.; the API uses the same parameter at `/api/maimai/kop8th`.

The first visitor to a version collects its current SEGA feed. After that, the first visit after 02:00 JST (International) or 07:00 JST (Japan) checks again. If the source has not published the expected daily update, or a request fails, another visit can retry after 30 minutes. An open visible tab checks every 30 minutes and on returning to the tab. There is no scheduler, Worker, or historical backfill: days without visitors can be missed.

Configure the existing `CF_ACCOUNT_ID`, `CF_KV_NAMESPACE_ID`, and `CF_API_TOKEN` on the Next.js server. The token needs KV read/list/write access to that namespace. Production returns an unavailable response if KV is not configured. Development without KV uses process-local memory, surviving HMR but not restarts. No additional secrets are required.

Moderators see “Add notice” directly below the ongoing-event message, or “Edit notice” when one is published. The shadcn Alert displays a single shared notice above both leaderboard versions. Its dialog supports publishing, editing, and removing up to 2,000 characters of plain text, preserving line breaks. `GET /api/maimai/kop8th/notice` is public; `PUT` accepts `{ "message": "…" }` and requires the existing `x-mod-token` header. An empty or whitespace-only message removes the notice. The record is saved without expiration at `maimai:kop8th:notice:v1`; removal writes a null record. Development without KV keeps it in memory across HMR. Saves are acknowledged only after storage succeeds; failures leave the editor open for retry. Visible tabs refresh the notice every minute and when returning to the tab. KV propagation may delay changes on other instances. The notice is separate from ranking archives and CSV exports.

New snapshots are stored without expiration under `maimai:kop8th:{international|japan}:snapshot:{sourceTimestampMilliseconds}:{sha256(archive)}`. Each value contains `collectedAt` and the complete original `payload`, including fields not used by the graph. Hashing the complete archive means concurrent collections with different contents write separate keys; writes to the same key contain the same value. Existing timestamp-only archive keys remain readable and are never migrated or rewritten. The `:check` key stores latest refresh timing/status separately. Archives are the source of truth; there is no mutable history index. Reads paginate and load at most six archive values concurrently, caching by full key so later-discovered variants are loaded too.

Cloudflare KV is eventually consistent. Simultaneous instances may collect different payloads for one timestamp; all competing archives remain stored. Leaderboard JSON and graph select one snapshot per timestamp: an existing timestamp-only archive takes precedence, otherwise the earliest collection wins, with archive key ordering breaking equal-time ties. Readers converge as keys propagate, without duplicate graph entries. Every successful source observation is archived, even if its source timestamp or contents are unchanged. The CSV includes all observations and identifies which ones are selected for leaderboard history. Non-selected observations never create extra graph points or score differences. This is not a distributed exactly-once collector. Storage and upstream failures are logged with a `[maimai:version]` prefix and surfaced in the page without deleting history.

Player identity is exact display name within a server. Search alone normalizes full-width text. Renames start new histories; duplicate names in a snapshot are excluded from connected series and still displayed in the standings. Leaving the latest KOP roster can mean dropping below its top 100; it is not treated as a ban or deletion. These players retain all saved scores in the chart, JSON snapshots, and CSV, and appear as “Not currently ranked” with a “Last recorded” score in the table. Only current players receive current ranks or qualifying positions. Gaps remain for snapshots where they were absent. The JSON `currentPlayers` list separates current membership from preserved score history. Original archives are preserved. After moderator deletions, remaining players in each affected leaderboard JSON snapshot are renumbered from 1 in their existing rank order, preserving source order for ties. Scores, DX scores, and source timestamps remain unchanged, so normal daily score differences remain and deletion creates no score update. Both source timestamp formats are interpreted as JST.

The latest roster is stored separately under `maimai:kop8th:{international|japan}:roster`, including source and collection timestamps. A new observation and its roster audit event must be saved successfully before the roster is published; archive-write failure leaves the previous roster intact. Readers apply a roster only to an archive with the same source timestamp, so a roster that propagates first cannot hide players in older cached history. This detects removals even when KOP changes the roster without advancing its timestamp. Older feeds and failed/invalid responses cannot replace the latest confirmed roster within a collector. Existing installations fall back to the newest archive until the next scheduled successful collection. Collection still follows the visitor-triggered daily schedule above; removals are not detected instantly.

Moderators authenticated with the existing `canvas-mod-token` localStorage setting see a Delete button on each player row. Confirmation hides all scores for that exact name from the leaderboard and graph in the selected version, including duplicate names. CSV exports retain those scores and mark them as removed. `DELETE /api/maimai/kop8th?server=ex|m` takes `{ "userName": "exact name" }` and requires the `x-mod-token` header, validated against `CANVAS_MOD_TOKEN`. Each new deletion writes a permanent immutable `maimai:kop8th:{international|japan}:deleted:{sha256(name)}:{sha256(marker)}` event containing the exact name and `deletedAt`. The event is both the moderation state and the audit record, so no separate audit write can disagree with a successfully applied removal. Repeated and concurrent removals remain separate when their timestamps differ. Existing name-only keys are still read and never rewritten; legacy missing timestamps remain unknown. Any saved event hides that exact name in that version, and future imports cannot restore it. This is a leaderboard visibility removal; raw archives and CSV scores remain intact. There is no restore control. Filtering runs after cache reads for leaderboard JSON. CSV exports all records in the version’s namespace and uses the same removal events to label every historical score row. If moderation storage is unreadable, both endpoints return 503 rather than presenting incorrect visibility or removal flags. KV propagation can delay visibility changes on other instances; open tabs update on their next refresh.

Placement arrows and score differences compare exact player names against the latest snapshot from the previous JST calendar day. Missing days, new/renamed players, and duplicate names have no change indicator. The graph defaults to score and selects the top ten; the searchable table supports sorting, left-side selection markers, and horizontal scrolling on mobile.

The info icon above the player table lists moderator-removed names for the selected version, or states that nobody has been removed. It is available to all visitors on hover, keyboard focus, and tap. The JSON response exposes these exact names in `removedPlayers`, read from the persisted deletion markers; players who merely leave the KOP roster are not included. Moderator-removed scores remain excluded from the leaderboard and graph, but appear in CSV with `removed=true`.

Audit events for roster observations and collection checks are stored without expiration under `maimai:kop8th:{version}:audit:v1:{roster|check}:{sha256(event)}`. Their envelope contains `schemaVersion`, `kind`, `recordedAt`, and `data`. Check events retain failure reasons, malformed received source payloads, and HTTP error/invalid-JSON response text with response metadata when storage is available; invalid source rows never enter leaderboard history. Latest roster/check keys point to their durable audit record via `auditKey`. Check events are written before reading the old latest-check key, preserving audit evidence through read-only outages without overwriting unreadable legacy state. CSV export follows audit/archive references and rejects missing referenced records instead of returning a silently incomplete result. Older latest-only metadata is archived before replacement. New audit history starts with this deployment: earlier overwritten events, missed upstream updates, and events during a complete storage outage cannot be reconstructed. Collection remains visitor-triggered. No migration rewrites or deletes existing archives.
